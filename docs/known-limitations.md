## 已实现但覆盖有限的能力

### 增量分析只按文件过滤（FR-005）

`--baseline <REF>` 会把分析范围收窄到相对该引用发生变化（新增或修改）的文件。
工作区没有对应的 Git 引用，因此对比方式是「基线树 ↔ 磁盘内容」。

限制：

- **删除的文件不会被分析**——它们不在磁盘上。若需要检查「被删掉的东西是否
  有人还在引用」，需要反向索引，当前不做。
- **本轮只分析变更文件，不分析被波及的文件**。改了 `pf-core` 不会把依赖它的
  `pf-report` 拉回分析范围；符号索引与调用图仍只基于变更文件构建，跨文件的边
  会缺失。这是有意的：需求文档 FR-005 的字面意思是「仅对必要的变更代码及相关
  依赖」。
- 目标不是 Git 仓库、或基线引用无法解析时返回错误（退出码 2），**不会**静默
  退化为全量分析。

变更影响范围本身已实现（FR-025）：给出基线时报告会多出「可能波及 N 个文件」
一段，列出反向可达集。为了让影响集不为空，模块依赖图是**按全项目**建的——
只用变更文件建图时，依赖它们的文件不在图里，反向可达集恒为空。因此配了基线的
审查在索引阶段与一次全量审查代价相当，规则执行阶段仍然只碰变更文件。

「波及范围」与「本轮看过的范围」是两件事，报告里分开写，JSON 里也分成
`impact.changed` 与 `impact.impacted` 两个字段，不混为一谈。

## 动态验证

### 变异测试测量的是测试套件，不是程序（FR-037）

`proofforge mutate` 回答一个问题：**项目自己的测试能不能发现一次行为变化**。
它不回答「代码对不对」，也不回答「测试够不够全」。

四条不可回避的边界：

- **通过率低不等于代码有 bug**。它只说明「改动没人发现」。测试可以因为覆盖
  不到而漏掉一个真实的 bug，也可以通过只断言不变式而不检查结果来「杀死」
  一个变异体——后者是弱测试，变异测试看不出来。
- **编译失败的变异体不计入分母**。它记 `invalid`，因为「测试没跑」与「测试
  跑了没发现」是两回事。把它算作幸存会凭空压低通过率，算作已杀死则会伪造
  「测试发现了问题」——后者曾经真实发生过：`cargo test` 在编译失败时同样非零
  退出，只读退出码就会把它记成已杀死。现在测试一失败就再问一次编译器
  （`Tool::Build`）来区分。
- **Python 项目产不出 `invalid`**。Python 适配器没有构建步骤，`Tool::Build`
  返回 `None`，于是改坏了语法的变异体会被记成已杀死。这是已知偏差，不是隐含
  假设。
- **变异体是词法生成的**（算术、关系、逻辑运算符互换，布尔取反，字面量加一）。
  `pf-verify` 不依赖 `pf-parser`（[`architecture.md`](architecture.md) 的单向
  依赖），因此拿不到语法树；需要改控制流、删函数体这类变异时要换实现。代价
  是可能命中泛型定界符（`Vec<i64>` 的 `<`）与一元负号（`-1` 的 `-`），产出的
  变异体编译不过并落入 `invalid`。

### 蜕变关系由人写，工具只负责跑（FR-039）

蜕变测试的形式是 `R(f(x), f(T(x)))`：`T` 是输入变换，`R` 是输出关系。两者
都必须由人写进规格文件——**从需求里自动推导蜕变关系需要语义理解**，当前不做
（同 FR-006）。

因此「未观察到违反」的含义是「人写的这条关系在这批输入上成立」，而不是
「这个函数满足它的规格」。规格写错了，结论照样是「未观察到违反」；规格文件
的校验只挡住两类明显错误（变换里没有 `{input}`、关系只提一个输出），挡不住
写错但自洽的关系。

## 静态分析

### 宏内部的调用不可见

`pf-symbol` 只提取 `call_expression` 节点。写在宏参数里的调用——例如
`assert_eq!(f(x), 1)` 中的 `f(x)`——在 Tree-sitter 的 Rust 语法里属于
`token_tree`，不会被提取。

影响：以 `assert_eq!(api(...), ...)` 为唯一调用点的公共 API 会被
`uncalled-public-api` 报告为「没有调用者」。这是假阳性，不是死代码。

绕法：把被调函数移到宏外（`let v = api(x); assert_eq!(v, 1);`）。
`fixtures/clean` 就是这么写的。

根治需要在 `pf-symbol` 里解析 `token_tree`，代价是要处理任意 token 序列。
在阶段三引入真实的测试执行之前不做这件事——那时「是否被调用」会由执行结果
回答，而不必依赖语法推断。

### 同名方法的解析是保守的

`pf-graph::CallGraph` 的启发式解析只在「按名字最后一段匹配且只有一个候选」
时接受。项目里有两个 `as_str()` 时，两者的调用都不会被解析。

这是有意选择：猜错的边会让循环依赖与死代码规则产生假结论，比漏报更糟。
未解析的调用记录在 `CallGraph::unresolved_calls()` 里，可以作为分析完整度的
证据。

### 只支持 Rust 与 Python

`pf-parser` 加载 Tree-sitter 的 Rust 与 Python grammar。其他语言的文件会被
跳过，并计入 `file_count`，但不产生符号与发现。报告不会因此标记为
`InsufficientEvidence`——这是已知的范围边界，不是执行失败。

### 单文件内联模块与文件级模块不区分归属

`mod tests` 与 `src/tests.rs` 在符号索引里都是普通作用域。模块依赖图按文件
建边，因此 `#[cfg(test)] mod tests` 里的 `use` 会算作文件级依赖。

### 资源管理只覆盖四个信号（FR-010）

`resource-management` 报 `mem::forget`、`Box::leak`、库代码里的
`process::exit`，以及「`Box::into_raw` 而无同文件 `Box::from_raw`」。

**锁使用错误与生命周期风险没有覆盖**：前者要知道哪个 guard 在哪个分支里被
持有，后者要跨函数跟踪引用的存活期，都需要过程间分析与类型信息。用文本匹配
去猜这两类问题会大量假阳性，而假阳性会让使用者学会忽略整条规则。

`into_raw` 那条的证据状态是 `Suspected` 并要求人工确认：裸指针是否泄漏取决于
调用方有没有把它还回来，而调用方在另一个文件里（红线 5）。

### 「未引用依赖」不是「不必要依赖」（FR-012）

`unused-dependency` 把清单里声明的依赖与源码里实际出现的路径根对一下，差值
就是候选。**它不能证明依赖可以被删除**：

- 只被宏使用的依赖在源码里看不到路径（`serde` 的 derive 展开前）；
- `pub use` 重新导出的依赖，自己的源码里反而不出现；
- 只服务于构建脚本、基准测试或条件编译平台分支的依赖同理。

因此每条发现都带 `needs_human_confirmation`，证据状态停在 `Suspected`。
另一个方向的已知漏报：以 `use crate::...` 之外的形式间接加载的依赖（例如
通过 `include!` 或 build script 生成的代码）看不到，会漏报——漏报好过误报。

### 架构规则按文件路径匹配，不按 crate（FR-024）

`architecture_rules` 的模式是路径通配符（`**` 跨目录，`*` 不跨），因为模块
依赖图按文件建边。这意味着：

- 规则要写到文件粒度才能生效，`crates/pf-report/**` 而不是「报告层」；
- 图只解析 `crate::` 前缀的内部引用，跨 crate 的边依赖模块名与文件路径的
  对应关系。引用方式不同（`use crate::domain::InputDomain`）时，边的存在性
  由 `pf-graph` 的解析能力决定，不由规则决定；
- **空规则集意味着不检查依赖方向**——工具不替项目预设分层。一份写着「检查了
  架构规则」却没有规则的规则集是误导，因此没有规则时该检查器根本不进入规则
  集元数据。

## 验证能力

### `inspect` 仍然只有静态证据

`inspect` 的结论全部来自确定性静态规则，因此 `EvidenceStatus` 只会是
`Suspected` 或 `StaticConfirmed`。**「代码确实长这样」不等于「缺陷已复现」**。
要拿到 `Reproduced` 必须跑 `verify`。

### 外部工具默认不执行

`adapters` 能运行 cargo / pytest / ruff，但 `inspect` 默认只做静态分析。
启用外部工具会让运行时间与结论依赖被审查仓库的工具链版本，因此需要显式
配置（AGENTS.md 安全红线 1：只运行由 `ToolAdapter` 生成的命令）。`verify`
反过来：它**必须**编译并执行目标代码，否则拿不到任何动态证据；此时它返回
证据不足（退出码 2），而不是通过。

### 沙箱隔离的是目录，不是 workspace

`Sandbox::isolate` 复制**目标目录本身**，不带上它的 workspace 根。因此把
`--target` 指向一个 workspace 成员 crate（例如本仓库的 `crates/pf-core`）时，
副本里的 `Cargo.toml` 仍在写 `edition = { workspace = true }`，而 workspace 根
不在副本里——`cargo test` 直接解析清单失败。

此时 `simplify` 报告的是「基线与补丁后都有测试失败，未经回归验证」，门禁返回
证据不足（退出码 2）。这是如实的结果：**基线跑不起来的时候，任何补丁都谈不上
被验证过**。要对 workspace 成员做动态验证，`--target` 需要指向 workspace 根，
或者让目标自己是一个独立可构建的包。

### 模糊测试是结果引导，不是覆盖率引导

`pf-verify::fuzz` 的反馈信号是「输入让程序违反不变式 / 崩溃 / 通过」，
**不是代码覆盖位图**。工业级覆盖率引导模糊测试需要编译器插桩（nightly 或
外部覆盖工具），那会把「能跑」变成「经常跑不起来」，与阶段三要证明的东西
（可复现的证据）相冲。

因此它擅长找「不变式明显不成立的输入」，不擅长深入罕见解路径。报告里的
`class_counts` 只反映观察到的行为类别，不代表覆盖率。

### 模糊测试不越出性质声明的输入域

每个变异结果都被 `InputDomain::clamp` 夹回 `PropertySpec.domain`。一条性质的
断言范围就是它声明的域：把 `i64::MAX` 上观察到的崩溃记在「`[-100, 100]` 上恒为
偶数」这条性质头上，等于让报告声称一个它并没有做出的断言。

代价是域外的潜在缺陷不会被发现——`double` 在 `i64::MAX` 上溢出崩溃是真实的，
但探索它要把域显式放宽。`FuzzOutcome::crashers` 给出的是域内崩溃输入，
`counterexamples` 给出的是域内违反输入，两者不混。

### 沙箱不是安全边界

`Sandbox` 提供的是**隔离**（独立工作区、凭据剔除、超时、不跟随符号链接），
不是**安全沙箱**。被审查仓库里的代码在沙箱内以当前用户权限执行，它能读当前
用户可读的文件、能发起网络连接。需求文档 9.2 的容器化隔离留待阶段六。

要在不可信代码上使用 ProofForge，请先在容器或 CI runner 里运行它。

### 性质由人写，不由需求推导

Agent Runtime（阶段四）已经能根据程序结构与测试反馈决定「跑哪些性质、先跑
哪个、何时停」，但它**不读需求文档的自然语言**。`verify --properties` 接受的
仍然是显式规格文件；`--requirements` 只作为追溯信息记录进报告。

把一句需求猜测成一条性质、再把结论说成「已验证」，是红线 5 禁止的事，因此这
条边界不会因为 Runtime 存在而移动。

### 驱动程序以字面量嵌入输入

生成的测试把输入值作为字面量写进源码。样本数很大时（数千）驱动程序会很大，
编译时间随之上升。默认样本数是 16；`samples` 是每条性质可配的。

### 反例缩减可能不收敛到最小

缩减按「整数朝零收缩、列表成块删除」的 ddmin 式候选序列推进，只在候选仍然
违反不变式时接受。如果某个候选让程序**崩溃**而不是违反不变式，它仍然算失败
（catch_unwind 把 panic 记为失败），因此这类反例也能被缩减。但缩减的判定
函数是整条不变式，不是单独的缺陷条件——一个输入可能因为另一个原因失败。
报告给出缩减规模与每一轮执行记录，具体是哪一步Accepted由人复核。

## 子命令的边界

| 命令 | 状态 | 说明 |
|---|---|---|
| `inspect` | 已实现 | 静态审查；门禁 0 / 1 / 2；唯一接受 `--config` 的子命令 |
| `verify` | 已实现 | 行为验证；没有性质可验证时返回证据不足（2），不伪造成功 |
| `simplify` | 已实现 | 只读分析默认开启；`--yes` 才写目标仓库 |
| `agent` | 已实现 | 任务由 Runtime 真实执行（`pf-verify` 的测试 / 性质 / 模糊执行器），不调用外部模型 |
| `rules` | 已实现 | 规范渲染、导入、冲突检测、豁免查询；全部只读 |

`simplify` 在没有工具链可用的目标上返回证据不足（退出码 2）：候选未经回归与
行为验证就不能被应用，这与「没有可以简化的东西」是两件事。

`simplify` 的工程指标比较只在**基线度量过的同一组文件**上进行。沙箱里除了项目
副本，还有回归与行为比较生成的驱动程序；不固定文件集的话，一次删除会被报告成
「代码规模 +31 行」——那数到的是工具自己刚生成的文件。

## 分析范围

### 没有用户可配置的路径排除清单

`pf-core::source::is_ignored_path` 跳过的是**构建产物与依赖目录**
（`target/`、`node_modules/`、`.git/`、锁文件等），这份清单是硬编码的，没有配置
入口。因此无法让 `inspect` 排除某个业务目录。

直接的后果：一个仓库里放着的**故意不合规的样本代码**会被如实报告，并正常参与
门禁。ProofForge 自己的 `fixtures/over-engineered` 就是这样——所以仓库根的
[`exemptions.toml`](../exemptions.toml) 按文件范围豁免了植入的样本，CI 另外断言
「被豁免的发现必须全部位于 `fixtures/` 下」。

需要按目录排除时，当前的做法是用 `--baseline` 收窄到变更文件，或者把样本放到
独立的仓库里。加一个 `exclude` 配置项是直接的改法，但它会改变「分析范围」这个
结论的含义，因此先记在这里，不偷偷加。

### 只有 `inspect` 读配置文件

`--config` 目前只被 `inspect` 接受。`verify` / `simplify` / `agent` 的设置都通过
各自的参数给出，因为这三者的配置面本来就小（超时、性质文件、候选数），再引入
一套文件优先级只会多一处「我以为设了其实没设」的地方。

## 报告与存储

### SARIF 覆盖到指纹与抑制，但不到 `codeFlows`

`pf-report` 输出的 SARIF 2.1.0 含规则、级别、消息、位置、
`partialFingerprints` 与 `suppressions`。指纹取 `FindingId`（由规则、类型、
标题与位置派生，与运行标识无关），因此 GitHub 代码扫描能做「只报告新增问题」
的去重；已豁免的发现以 `suppressions` 表达，仍然出现在结果里，可审计。

未实现的是 `codeFlows`（数据流路径）与 `relatedLocations`：当前规则产出的是
结构事实，不是过程间的数据流，硬画一条流程线等于伪造证据。

### 存储层只有增量迁移，没有版本化迁移链

`pf-store` 用 `CREATE TABLE IF NOT EXISTS` 建表，并对新增列执行
`ALTER TABLE ADD COLUMN`（启动时检查 `pragma_table_info`），因此旧库可以平滑
升级。但这只覆盖「加列」：改列类型、拆表、回滚都需要手动处理。在多用户服务化
之前够用。
